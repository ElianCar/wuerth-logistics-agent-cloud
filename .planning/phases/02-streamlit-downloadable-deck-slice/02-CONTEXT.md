# Phase 2: Streamlit Downloadable Deck Slice - Context

**Gathered:** 2026-06-21
**Status:** Ready for planning
**Mode:** Smart discuss defaults accepted under autonomous `mode: yolo`

<domain>
## Phase Boundary

This phase exposes the Phase 1 backend PowerPoint exporter in the existing Streamlit result view. A user who has a successful validated analysis run can create a Wuerth PPTX, see progress while it is created, and download it afterwards. The phase should not expand the slide contract, add a slide designer, or move rendering logic into Streamlit.

</domain>

<decisions>
## Implementation Decisions

### Button Placement And State
- Place the PPT controls near the existing CSV and Excel export controls for a result record so users understand all exports belong to the same validated query result.
- Use a two-step stateful flow per record: `Create PPT` triggers backend generation, then a `Download PPT` control appears for the generated bytes.
- Store generated PPTX bytes and metadata in `st.session_state` keyed by a stable record/run identifier so reruns do not immediately lose the generated deck.
- Keep the UI quiet and utilitarian: no hero panel, no extra presentation-builder page, and no decorative cards around the export controls.

### Eligibility, Errors, And Warnings
- Do not show PPT export as available for records that fail Phase 1 backend eligibility. Surface a short reason near the export controls rather than letting users download broken output.
- If generation fails because the template is invalid or rendering fails, show the backend `unavailable_reason` plus warnings from `PresentationExport` in Streamlit without crashing.
- Template warnings such as known think-cell OLE entries should be visible but non-blocking when `PresentationExport.available` is true.
- Keep user-facing messages short and action-oriented; detailed audit fields can stay in expanders or captions.

### Deck Options Exposed In UI
- Phase 2 should be one-click by default and should not expose slide-order, layout, or chart-type controls.
- Do not expose `include_closing` yet. Agent 09 Closing remains opt-in in backend code and can be enabled later if there is a clear user need.
- Use whatever dynamic slide spec the backend returns. The UI should not try to inspect or mutate slide contents.
- Keep file naming from `PresentationExport.filename`; do not create a separate Streamlit naming scheme.

### Verification Strategy
- Automated tests should cover Streamlit helper behavior where possible without starting a full browser session.
- Manual Streamlit verification should confirm the visible `Create PPT` to `Download PPT` transition, filename, MIME type, warnings, and ineligible-record behavior.
- A seeded/mock successful record is acceptable for UI verification if live DB/API setup blocks repeatable checks. The record must still match the backend eligibility contract.
- Verification must confirm `streamlit_app.py` only calls the backend exporter and does not contain PPTX rendering logic.

### the agent's Discretion
- The planner may choose the exact helper names and session-state key shape as long as they are deterministic and local to `streamlit_app.py`.
- The planner may decide whether to add focused helper tests in `evaluation/test_presentation_export.py` or a new Streamlit-specific test module.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/agent/presentation_export.py` exposes `build_presentation_export`, `can_export_presentation`, `PresentationExport`, and `PPTX_MIME_TYPE`.
- `streamlit_app.py` already renders records through `render_record(record, index, config)` and exports CSV/XLSX beside the result dataframe.
- Existing record data already includes `query_result`, `reporting_result`, `source_tables`, `run_id`, and SQL fields needed by the backend exporter.

### Established Patterns
- Streamlit session state is managed inside `streamlit_app.py`; new UI state should stay there.
- Export buttons are currently placed near the result preview and use stable keys based on the record index.
- Error handling in Streamlit is intentionally resilient: expected invalid states should show messages rather than raise.
- Tests use `unittest` under `evaluation/test_*.py`; broad syntax verification uses `python -m compileall app src scripts streamlit_app.py evaluation`.

### Integration Points
- Add imports from `src.agent.presentation_export` to `streamlit_app.py`.
- Integrate PPT controls near lines where CSV and Excel exports are rendered for records with rows and columns.
- Use Phase 1 backend availability and result fields rather than duplicating eligibility logic in Streamlit.
- Existing backend export tests remain the baseline; Phase 2 should add coverage for UI helper behavior and Streamlit boundary constraints.

</code_context>

<specifics>
## Specific Ideas

- The button label must be `Create PPT` while generation is pending or running.
- After generation succeeds, the UI must switch to `Download PPT`.
- The UI should remain dense and work-focused, consistent with the existing operational Streamlit app.
- Canonical refs downstream agents should read: `.planning/PROJECT.md`, `.planning/REQUIREMENTS.md`, `.planning/ROADMAP.md`, `.planning/STATE.md`, `.planning/phases/01-deterministic-backend-deck-slice/01-CONTEXT.md`, `src/agent/presentation_export.py`, `streamlit_app.py`, and `evaluation/test_presentation_export.py`.

</specifics>

<deferred>
## Deferred Ideas

- UI controls for optional closing slide, slide presets, and visual style choices are deferred until after the basic create/download path proves useful.
- More complex chart support, top-N readability, and fallback slides stay in Phase 3.
- App-wide authentication and persistent user roles stay out of Phase 2.

</deferred>
